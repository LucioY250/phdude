# The example workspaces

`examples/` holds four finished PhDude workspaces. They are not fixtures and they are not
hand-written YAML: each one is generated by driving the same use cases the CLI drives, against a
fixed clock, so what you read in the diff is what the tool actually produces.

They exist to be compared. A thesis about note-taking apps, a two-wave household survey, a
benchmark paper and an archival study are as far apart as research gets, and nothing in `src/`
knows which of them it is reading. The same `status`, `next`, `gaps`, `health` and `ready`
answer all four; the only things that differ are which packs the workspace applied and what its
researcher wrote down.

```
examples/
├── generic-thesis/                 # the tour: every gap kind, the whole pipeline
├── quantitative-social-science/    # survey data, an open fact conflict
├── machine-learning/               # a benchmark table, a contradiction in the literature
└── qualitative-humanities/         # archival sources, a disputed pair, no statistics
```

## What each one is

| | packs applied | venue | data | the open problem |
|---|---|---|---|---|
| `generic-thesis` | — | `generic-thesis` | survey CSV, one analysis | a `sample_size` conflict across three surveys |
| `quantitative-social-science` | `quantitative` | `generic-thesis` | attendance CSV, one analysis | a `households_surveyed` conflict across two waves |
| `machine-learning` | `computer-science` | `ieee` | benchmark runs CSV, one analysis | two preprints that cannot both be right |
| `qualitative-humanities` | `humanities`, `qualitative` | `generic-thesis` | none | two folios that attribute the same founding differently |

**`generic-thesis`** is the tour. It is generated to reach every gap kind `phdude gaps` can
report, so its `gaps` output doubles as the worked example of each one.

**`quantitative-social-science`** is a two-wave household survey about attendance at
participatory budgeting assemblies. It carries a registered dataset, an analysis run under the
execution policy, a table built from one result and a figure drawn from another, and one open
fact conflict: the two waves report different denominators, and a Decision proposing which one is
canonical is waiting for a researcher.

**`machine-learning`** is a benchmark paper about post-training quantization. Its sources are
arXiv preprints addressed by their arXiv ids, its recorded literature search ran against the
arXiv provider, and accepting a candidate out of it required the preprint approval the research
policy demands. The benchmark results table is built from a `RESULT`, not retyped from one. The
open problem is a contradiction: two preprints report the same recipe and disagree, so both
claims sit at `disputed` with no Decision.

**`qualitative-humanities`** is an archival study of a provincial reading society. There is no
dataset, no analysis and no figure — the sources are transcribed letters, the evidence carries
box-and-folio locators, and the one recorded fact is a shelfmark rather than a measurement. Two
letters written nine months apart attribute the society's founding to different people; the
disputed pair is recorded, a Decision proposing how to resolve it is proposed, and it stays open
because preferring one folio over another is an argument a historian makes in the text.

Every one of the four also carries an author profile learned from an approved writing sample, a
manuscript whose introduction went through draft, revision, prose report and approval behind a
Decision, and one open review finding.

## Reading one

Clone the repository and run the CLI inside any of them. Nothing is written:

```
cd examples/machine-learning
phdude status
phdude next
phdude gaps
phdude health
phdude ready          # exits 2: none of the four is ready to submit
phdude knowledge trace CLAIM-<id>
```

`phdude ready` exits `0` when a workspace could be submitted and `2` when something blocks it.
All four exit `2` on purpose: an example that had already answered every question would show the
end of the work rather than the middle of it.

## Regenerating them

```
npm run example        # examples/generic-thesis
npm run examples       # the three cross-field ones
npm run example:all    # all four
```

Every generator is deterministic: a fixed clock advancing one second per call, a fixed source
file mtime, a stubbed `fetch` answering the recorded literature searches from a canned response,
and an execution runner pinned to this process's own `node` with its duration zeroed. Running a
generator twice into a fresh directory produces byte-identical files, and
`tests/integration/make-examples.test.js` asserts both that and the match against what is
committed. Nothing reaches the network.

Committed policies stay closed (`execution.enabled: false`, `network.enabled: false`), exactly as
`phdude init` writes them. The generators pass the flags a researcher would have to pass by hand.

The mechanics — the clock, the git and fetch stubs, the pinned runner, and the wrappers over the
use cases whose shape is the same in every field — live in `scripts/lib/example-builder.mjs`. A
profile supplies only the research: a title, the source files, and one `build` function.
`scripts/make-example.mjs` holds the thesis profile; `scripts/make-examples.mjs` holds the other
three.

## The goldens

`tests/golden/expected/<example>/{status,next,gaps,health,ready}.txt` pins the exact output of
each of the five reports for each cross-field example, rendered against a fixed present so an age
measured in days renders the same today and in a year. After a deliberate change to a renderer, a
use case or an example itself:

```
npm run example:all
UPDATE_GOLDEN=1 node --test "tests/golden/*.test.js"
```

Then diff `tests/golden/expected/` and confirm the change is the one you meant.

`analysis/out/`, `tables/out/` and `figures/out/` are committed inside the examples even though a
real workspace's `.gitignore` excludes them: an example is a finished workspace a reader clones
and looks at, and `phdude repro check` has to find nothing stale in it. A new output path added
to an example has to be `git add -f`ed the first time.

## Why they are the field-agnosticism test

PRD §120 asks that PhDude be usable across materially different disciplines without core forks.
That is not something a README can assert. `tests/integration/make-examples.test.js` reads every
module under `src/`, strips the comments, and fails if the name of any field pack or any of the
three disciplines appears in what is left. A field reaches PhDude through a pack and an example,
never through a branch in the core.
